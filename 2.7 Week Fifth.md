<h2 id="第-5-周：按“问题驱动”读源码">第 5 周：按“问题驱动”读源码</h2>
<blockquote>
<p>核心目标：不再顺着源码读，而是用“问题 → 路径 → 结论”打通关键机制</p>
</blockquote>
<h2 id="问题-1：offer-为什么会失败？">问题 1：<code>offer()</code> 为什么会失败？</h2>
<p>沿着这条线看：</p>
<ul>
<li><code>Publication.offer</code></li>
<li>back pressure 判断</li>
<li>position limit</li>
<li>publisher limit</li>
<li>flow control</li>
</ul>
<p>你要最终能解释：</p>
<ul>
<li><code>BACK_PRESSURED</code></li>
<li><code>NOT_CONNECTED</code></li>
<li><code>ADMIN_ACTION</code></li>
<li><code>CLOSED</code></li>
<li><code>MAX_POSITION_EXCEEDED</code></li>
</ul>
<p>这些返回语义是怎么来的。<br>
配置项文档和变更日志里也能看到 publication / image 行为一直在演进，比如 <code>ExclusivePublication#revoke</code>、<code>Image#reject</code> 等。</p>
<hr>
<h2 id="问题-2：消息丢了是怎么补的？">问题 2：消息丢了是怎么补的？</h2>
<p>沿着这条线看：</p>
<ul>
<li>Receiver 怎么发现 gap</li>
<li>什么时候发 NAK</li>
<li>Sender / retransmit handler 怎么补发</li>
<li>reliable / unreliable 的差异</li>
</ul>
<p>Transport Protocol Specification 和 Flow/ Congestion Control 文档就是这一块的理论基础。</p>
<hr>
<h2 id="问题-3：慢在哪里？抖动在哪里？">问题 3：慢在哪里？抖动在哪里？</h2>
<p>沿着这条线看：</p>
<ul>
<li>idle strategy</li>
<li>thread mode</li>
<li>counters</li>
<li>duty cycle stall</li>
<li>error log / CnC</li>
</ul>
<p>官方的 Monitoring and Debugging 文档提到可通过 <strong>ErrorStat</strong> 读错误日志，也强调了 CnC 和 counters 在调试中的作用。</p>
<hr>
<h2 id="一句话模型">一句话模型</h2>
<blockquote>
<p>不读代码结构，读“问题链路”（从现象 → 机制）</p>
</blockquote>
<hr>
<h2 id="本周三大问题">本周三大问题</h2>
<hr>
<h3 id="️⃣-offer-为什么会失败？">1️⃣ offer() 为什么会失败？</h3>
<blockquote>
<p>本质：写入受限（流控 / 状态 / 生命周期）</p>
</blockquote>
<hr>
<h4 id="阅读路径">阅读路径</h4>
<pre><code>Publication.offer
→ back pressure 判断
→ publisherPosition / limit
→ flow control（senderLimit）
</code></pre>
<hr>
<h4 id="返回码语义">返回码语义</h4>
<pre><code>BACK_PRESSURED
→ senderLimit 已到（接收端限制）

NOT_CONNECTED
→ 还没建立连接（没有 Image / SM）

ADMIN_ACTION
→ Driver 正在切 term / 状态变更

CLOSED
→ Publication 已关闭

MAX_POSITION_EXCEEDED
→ 超过最大 position（term 用尽）
</code></pre>
<hr>
<h4 id="一句话">一句话</h4>
<blockquote>
<p>offer 失败 = 当前“不能继续写”</p>
</blockquote>
<hr>
<h3 id="️⃣-消息丢了怎么补？">2️⃣ 消息丢了怎么补？</h3>
<blockquote>
<p>本质：Receiver 发现 gap → NAK → Sender 重传</p>
</blockquote>
<hr>
<h4 id="阅读路径-1">阅读路径</h4>
<pre><code>Receiver
→ 检测 offset 不连续（gap）
→ 发送 NAK

Sender
→ 收到 NAK
→ retransmit handler
→ 重发缺失数据
</code></pre>
<hr>
<h4 id="关键机制">关键机制</h4>
<pre><code>gap detection（发现丢包）
NAK（请求重传）
retransmit（补发）
</code></pre>
<hr>
<h4 id="reliable-vs-unreliable">reliable vs unreliable</h4>
<pre><code>reliable：
  会 NAK → 保证完整

unreliable：
  不重传 → 允许丢
</code></pre>
<hr>
<h4 id="一句话-1">一句话</h4>
<blockquote>
<p>丢包 = Receiver 发现 → NAK → Sender 补发</p>
</blockquote>
<hr>
<h3 id="️⃣-慢在哪里？抖动在哪里？">3️⃣ 慢在哪里？抖动在哪里？</h3>
<blockquote>
<p>本质：线程调度 + idle 策略 + 流控</p>
</blockquote>
<hr>
<h4 id="阅读路径-2">阅读路径</h4>
<pre><code>idleStrategy
threading mode
duty cycle（doWork）
counters
error log / CnC
</code></pre>
<hr>
<h4 id="关键点">关键点</h4>
<pre><code>idleStrategy：
  busy spin / yield / sleep（影响延迟）

thread mode：
  shared / dedicated（影响隔离）

duty cycle：
  doWork 执行时间（是否 stall）

counters：
  position / limit / back pressure

CnC：
  driver 状态 + error log
</code></pre>
<hr>
<h4 id="常见问题定位">常见问题定位</h4>
<pre><code>发送慢：
  publisherPosition ≈ senderLimit

消费慢：
  receiverPosition ≫ subscriberPosition

丢包：
  nakCount 增加

线程卡顿：
  duty cycle 无法及时执行
</code></pre>
<hr>
<h4 id="一句话-2">一句话</h4>
<blockquote>
<p>慢 = CPU / 调度问题；抖 = 不稳定的 doWork + idle 策略</p>
</blockquote>
<hr>
<h2 id="本周三条主线">本周三条主线</h2>
<pre><code>写不进去 → offer / back pressure
丢数据   → gap / NAK / retransmit
性能问题 → idle / thread / counters
</code></pre>
<hr>
<h2 id="本周目标">本周目标</h2>
<p>你要能讲清：</p>
<ol>
<li>offer 为什么会失败（每个返回码含义）</li>
<li>丢包是怎么被发现和恢复的</li>
<li>系统慢 / 抖动怎么定位</li>
<li>counters / CnC 在调试中的作用</li>
</ol>
<hr>
